# ARM — Milestones

Dependency-ordered. Toolchain details for M1–M4 and M15: [`SPEC-FIRST.md`](SPEC-FIRST.md).
The `arm` CLI grows with every milestone.

- [x] M1 — **Spec toolchain**: one POST + one GET on `Message`; mise, root `package.json`, Hey API client, route-coverage + contract tests, minimal `arm` binary
- [x] M2 — **Backend generator**: our own TypeSpec emitter generating the backend surface (records, typed `IHandler` interfaces, route mapping, validators, result → status mapping) into `artifacts/`; migrate `Message` onto it
- [x] M3 — **SSE**: typed events with `type`, server-side filters, `Last-Event-ID` replay, `arm events`
- [x] M4 — **Sessions core**: create/get/search/kill/delete, state machine, queue + slots, timeouts, FakeProvider; search as `POST …/search` (`QUERY` moved to VISION); error envelope + typed multi-status responses; `Idempotency-Key`; **`Message` example removed entirely** — the API contains only ARM entities. In memory until M5
- [x] M4b — **Providers & models** (contract agreed 2026-10-12; built 2026-10-25, after the web UI's repos, which touches the same composer): `GET /api/providers`, each provider with its models: ids plus display names (optional in the server's configuration, falling back to the id; always present in the API). The models are configured per environment, and a session naming a model its provider doesn't list is refused (400 `UNKNOWN_MODEL`, like `UNKNOWN_PROVIDER`). A model's context window is left out until context use is built (M6). Clients: `arm provider list`, and the web UI's model dropdown ("Opus (Claude Code)") as in the sessions mock
- [x] M5e — **Repos** (agreed and done 2026-10-12, built by an ARM agent on beta over three review rounds; API and CLI on prod the same day; the web UI's part built from its own mock (`mocks/repos.html`), awaiting the owner's approval of the built UI; after M4b: it's what makes ARM usable for other repos, and for several agents on one): a session names zero or more git repos (`repos: [{ url, ref? }]`, by URL; a registry of repos with names can come later) and ARM's own code, not the agent, checks them out before the agent starts. One shared copy of each repo on the VM (bare, cloned on first use, fetched whenever a session that names it starts: one fetch per repo at a time), and a worktree per session in its workplace (`work/<repo name>`) on a new branch named for the session (`arm/<short id>`), from `ref` (a branch, tag or commit; unset: the default branch). The session shows its `repos` as given, each with the `folder` and `branch` ARM gave it (added 2026-10-12 for the web UI, so no client repeats the naming rules; the commit it started from can be added later). A checkout that fails (no access, unknown ref) fails the session before the agent runs, with git's error. The agent starts in the workplace, as today, with each repo in its own folder there; pushing is its own job, as today. Continuing a session (M11) keeps its worktrees and syncs nothing; deleting it removes them and keeps the branch in the shared copy. ARM never rebases or merges; checking a finished session's branches (unpushed, behind, conflicts) is a later step. Needs git access to every repo a session may name (today's deploy key covers ARM's repo only). Clients: `arm session create --repo <url>[#ref]` (repeatable; `#`, since SSH URLs contain `@`), and in the web UI (from its own mock, `mocks/repos.html`) a `repos` button and panel in the composer and a `repos` row in the session page's Details
- [x] M5 — **Persistence**: sessions in SQLite through EF Core (A5), migrations at startup; after a restart, working sessions are killed (source `system`) and queued ones queue again
- [x] M9 — **Claude provider**, moved ahead of M5a (2026-09-26): its process model decides what gentle restart has to do. Integration decided after spikes (A10): the CLI's `stream-json` protocol directly, no ACP adapter or Agent SDK sidecar. First cut: a `claude` provider that runs the locked-down CLI per session (the ARM session id as Claude's session id, the model passed through, the final result as the summary, the raw output kept per session), tested LLM-free against a stub CLI replaying recorded output (TESTING L2). Then Claude Code on the VMs: the latest release verified and staged in the bundle by a `claude-code` pipeline step (beta and prod run the same version; rollback included), logged in with `CLAUDE_CODE_OAUTH_TOKEN` from a pipeline secret per environment; then provider health: a provider refusing agents (bad token, usage limit, outage) pauses, its sessions queue and retry (`GET /api/providers/health`, `arm provider health`, `provider.health` events; 2026-09-26). Steering, interrupt and approvals use the same channel and land with their milestones (M11, M8)
- [x] M5a — **Gentle restart**: server exits, agents survive, new server re-attaches (event replay completes in M6). A supervisor per session, a separate internal executable in the release, owns the agent's stdio, logs its output and exit code to disk and lets a restarted ARM reconnect over a socket; if the supervisor is gone too, ARM resumes the provider session (A10). Built 2026-09-27 as [`GENTLE-RESTART.md`](GENTLE-RESTART.md) (`olve-arm-supervisor`, Native AOT); a session spanning a server restart verified on beta
- [x] M5d — **Coding sessions** (done 2026-09-27: so ARM's own agents can do ARM's work instead of base Claude Code). Registered environment variables (`GET/PUT/DELETE /api/env/{name}`, a `default` flag: default ones go to every agent, others when a session names them in `useEnv`) plus a session's own `env`; values are taken when the session is created, names ARM sets itself are reserved, and none of it is secret (secrets are in VISION). All of Claude Code's built-in tools are on, with the VM as the sandbox and a persisted workplace: agents install their own toolchain (mise), clone the repos they need and push over SSH with a deploy key (`GIT_SSH_COMMAND`, a default variable on beta) under Oliver's git identity. Proven on beta: an agent fixed a supervisor bug with a test (merged) and pushed a README change itself (merged). CLI: `arm env set/list/delete`, `arm session create --env K=V --use-env NAME`; the web UI's env is its own item under Web UI
- [x] M5b — **Session transcript** (the log view, a core feature; done 2026-09-27: API, `arm session conversation`, the web UI's session page; notices, Claude Code's own messages to the agent, as their own optional kind; following live comes with M6): every turn of a session (user prompt, agent text and thinking, tool calls with arguments and results, messages) stored per session and read with one call (`GET /api/sessions/{id}/conversation`), plus counts (turns, messages, tool calls). Conversation content lives only here and in its events, never on `Session` or in lifecycle events (the `summary` field went on 2026-09-26); the `claude` provider already keeps each session's raw output (`output.jsonl`) to build from; the fake provider scripts turns so it's built LLM-free. Clients: `arm session conversation <id>` and the web UI's session detail ([`UI-REFERENCE.md`](UI-REFERENCE.md)). Following a running session live can come with M6: clients subscribe to the events and fetch the snapshot in parallel, buffer events until the snapshot arrives, then apply the ones it doesn't already contain (dedupe by a per-session sequence number that entries and events both carry, e.g. `seq` vs the snapshot's `lastSeq`). The web UI's session list gets the same treatment (today it can lose or overwrite an event while its first search loads)
- [x] M5f — **Session activity** (agreed and done 2026-10-12, built by an ARM agent on beta; on prod the same day: the Overview's log preview, which M5b left unbuilt): what a session's agent is doing right now, for people to glance at, as its own small read next to the full conversation: `GET /api/sessions/{id}/activity?limit=3` returns the most recent lines, each a `kind` (`text`: something the agent said; `tool`: a tool it called, as a name and a short form of what it was called with; `error`: a failed tool call or turn, or why the session failed) and one line of `text` (no line breaks, shortened when long). Thinking, notices, prompts and tool results that didn't fail are left out. Picked in code from the stored conversation, no LLM; nothing of it goes on `Session`. Clients: the web UI's Overview shows it on running sessions' cards as in the mock (last 3 lines, filling from the bottom, expand, wrap; re-read every few seconds until M6's events), `arm session activity <id>`, and `arm session list` can show the latest line
- [x] M11 — **Messaging** (agreed and done 2026-09-27, built by an ARM agent on beta; revive moved to VISION): `POST /api/sessions/{id}/messages` (`{ text, caller }` → 202 `{ delivery }`) talks to a session's agent. While it works the message goes straight to it (`delivered`; it sees it after its current step). While it's queued the message is held and sent when its agent starts, after the prompt (`pending`). Once it has ended (completed, failed or killed) the session continues with it (`continued`): back to `queued`, same id and conversation, the agent resuming its context (`claude --resume`) with the message as what it's told next, and a new run (timeout included). Only a session cancelled before it ever started has no agent to continue (409). Messages show in the conversation as prompts. Clients: `arm session message <id> "text"`, a message box on the session page (mock first)
- [ ] M10 — **ARM's tools** (moved up 2026-09-27: ARM's own tools replace Claude Code's built-ins, which M5d turns on, as soon as possible; agreed 2026-10-26, skills and external tools split off into M10b): a session names the tools it gets, by name (`tools: ["arm_bash", "arm_file_read", …]`, like the `allowed_tools` of MCP connectors). A session that names any gets only ARM's tools: every built-in of the provider is off, Task (subagents), TodoWrite, web tools and image reading included (accepted). A session that names none keeps today's built-ins; making ARM's tools the default is a later decision (once it flips, missing and `[]` may need to mean different things, so "reasoning only" stays expressible). The tools: `arm_bash` (stateless: every call a fresh shell in `workingDir`, the workplace by default; `timeoutSeconds`, default 120, max 600, killing the process group; output capped, keeping head and tail; room left for background jobs later), `arm_file_read` (offset/limit, numbered lines), `arm_file_edit` (exact string, unique unless `replaceAll`), `arm_file_create` (refuses an existing file), `arm_file_delete` (a directory only with `recursive`), `arm_file_copy` and `arm_file_move` (files and directories, refusing an existing target unless `overwrite`). Relative paths resolve from the workplace, absolute ones go anywhere (confining them protects nothing while `arm_bash` exists; policies are M8's). Every call runs, as today, with the VM as the sandbox. They're served by `olve-arm-tools`, an internal executable in the release (Native AOT, like the supervisor) that the agent starts as a stdio MCP server per session: it survives an ARM restart with the agent, and M18 runs the same binary on a target. Transcripts and activity show `arm_bash`, not the provider's `mcp__arm__arm_bash` (stripped at the provider seam), and the tools' arguments use the field names the previews already know. `GET /api/tools` lists them (name, description); a session naming an unknown one is refused (400 `UNKNOWN_TOOL`). To check in a spike before building: whether the tools server inherits the session's environment (`env`, `useEnv`, `GIT_SSH_COMMAND` for pushing), whether the agent sends a tool-call id (a call must not run twice, also when a resumed agent starts a new tools server: GENTLE-RESTART), whether its MCP client cuts calls off before 600 s, and that a killed session's processes die with it. Clients: `arm tool list`, `arm session create --tool X` (repeatable), and in the web UI (mock first) a `tools` panel in the composer next to `env` and `repos` and the tools in the session page's Details. Done when an ARM agent on beta finishes a real ARM task with ARM's tools only
- [ ] M10b — **Skills & external tools** (split off M10 on 2026-10-26; still ahead of M6): the skills registry and `arm_skill_list`/`arm_skill_load`, and external MCP servers a session can turn on, listed in `GET /api/tools` next to ARM's own. To be designed
- [ ] M6 — **Event bus**: all SPEC event types, filters, replay incl. across restart
- [ ] M7 — **Auth**: fine-grained permissions composed into roles; default roles read-only / operator (start, kill, approve; no configuration) / admin; session-scoped agent tokens; local tokens (A3)
- [ ] M8 — **Approvals**: approval tools, policies (versioned), approve/deny, waiting calls (design them so a long wait can later become a sleeping session rather than a timeout, see VISION "Sleeping sessions"); shell classifier as a **separate low-dependency package** (wrap an existing parser, e.g. tree-sitter-bash / mvdan/sh / bashlex, else from scratch)
- [ ] M17 — **Files** (added 2026-09-27; later, after the MVP's core): files travel with messages, both ways. You → agent: a prompt or message can carry files (`arm session create --file`, `arm session message --file`, attach in the web UI's composer and message box); they land in the agent's workplace (and it's told where), and images and PDFs also go to the model as part of the message, so it sees them directly. Agent → you: its reply can carry files you download from the conversation. How the agent attaches one (an outbox, an ARM tool, a file it names) and how attachments show on conversation entries is designed when it's picked up. No size limits in a first cut (retention, M14, cleans up)
- [ ] M12 — **Completions** (optional schema validation, retries)
- [ ] M13 — **Codex provider** (re-evaluate the current CLI first)
- [ ] M14 — **Retention**: 6-month retention, hot/cold tiers, compressed archive
- [ ] M5c — **Parent sessions** (moved after M14 on 2026-09-27: using ARM for ARM's own work comes first): `CreateSession` accepts an optional `parentId` and the session carries it; search can filter by parent. When a parent ends (completed, failed, cancelled or killed), its children end too: queued ones are cancelled, working ones killed, source `system`, reason naming the parent. ARM gives every agent its own session id in the environment (`ARM_SESSION_ID`), so an agent's `arm session create` picks it up as the parent automatically; `--parent <id>` overrides it and `--no-parent` opts out. Web UI: children nested under their parent (rail, fold, "+N ended"), as in the mock; the UI has no way to set a parent. (Agent-started subagents are a different thing, see VISION "Subagents")
- [ ] M15 — **API versioning** (B3)
- [ ] M16 — **Typed ids** (after the MVP; agreed 2026-09-26): ids as Olve.Utilities `Id<T>` (`Id<Session>`, later completions, approvals, …) instead of bare `Guid`s, so ids of different things can't be mixed up. Through the emitter: the `Id<T>` decorator already planned in `SPEC-FIRST.md` (generated models, route parameters, JSON converters, conformance tests), then the backend (store, runtime, handlers) moves over in one pass. The wire format stays a UUID string
- [ ] M18 — **Remote targets** (added 2026-10-26; post-MVP, after M10, whose tools it builds on): Claude Code keeps running on ARM's VM (auth, supervisor, gentle restart unchanged) while its tools act on another machine over SSH. A registry of targets (host, user, a key ARM holds); a session names a target and a folder there. ARM's own tools (M10) take the target: they run from an MCP tools server ARM starts on the target, over one multiplexed SSH connection. Repos (M5e) are checked out on the target. Each target gets a dedicated user, like `arm-agent`. Prototype first: on beta, sshfs at the same path plus a `CLAUDE_CODE_SHELL` SSH wrapper, to learn what leaks. Replaces VISION's "Remote SSH executor"; settles OPEN-QUESTIONS A6

## Web UI

The approved target for the sessions screen is the mock
[`src/frontend/mocks/sessions.html`](../src/frontend/mocks/sessions.html) (open it in a browser;
its banner switches between the target design and what today's API supports). Each milestone
builds its part of it in the web UI, alongside its API and CLI (STANDARDS, Clients); UI work
stays mock-first, so parts the mock doesn't show get a mock of their own first. The mock is
deleted once the whole screen is built and approved.
